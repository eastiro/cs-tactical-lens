# CS Tactical Lens：一个可复现的 CS2 Demo 接触前结构分析工作台

## 摘要

CS Tactical Lens 是一个面向研究的个人项目，为职业 **Counter-Strike 2**（CS2）比赛数据构建了可审计的分析管线。它最核心的设计选择，是把每项页面摘要连接到具体 Demo 的回合、雷达图和选手轨迹证据。

当前本地语料包含 135 个已验证地图 bundle，并生成覆盖 7 张比赛地图的 117 个 team-map research profile。每个 profile 以经济感知观察窗口（全起 20 秒、半起 12 秒、手枪/刚枪/Eco 15 秒）聚合同一队伍在同一地图上多场比赛的接触前站位数据。公开 Showcase 包（2.78 MB）可在不下载完整 67 GB 本地语料的情况下演示回放管线。系统通过 350 项自动测试和 20/20 发布审计。

工作台明确停止在战术意图推断、胜负预测或"战队默认战术"声明之前。它只提供描述性的、可审计的证据，说明选手在首次交火前站在哪里——仅此而已。

---

## 问题与动机

职业 CS2 Demo 包含丰富的站位、经济和事件数据，但在多场比赛之间提取有意义的比较信息面临技术挑战：

- **Demo 解析需要受控的数据契约。** 原始 .dem 文件需要 Awpy 等专门解析器；解析器或游戏格式变化后，输出结构可能变化，需要重新校验。
- **单场描述的适用范围有限。** 单场比赛受对手风格、地图阵营和比赛上下文影响。聚合多场并不能消除这些影响，但能把重复观测和样本覆盖量明确呈现出来。
- **脱离证据的聚合结果难以复核。** 如果摘要不能连接到底层回合与游戏状态，读者就无法独立确认一个“倾向”究竟来自接触前站位还是后续事件。
- **项目需要明确的操作性分析单位。** 本项目不声称建立行业标准，而是定义并一致使用“队伍 × 地图 × 接触前样本”这一分析单位。

本项目通过定义可复现的分析单位——**team-map 接触前 profile**——并展示一条从原始 Demo 到可审计比较证据、已为公开发布做准备的可检查管线来回应这些需求。

---

## 研究问题

1. **接触前站位：** 职业 CS2 队伍在首次交火前的 12–20 秒内，如何将选手分布在地图各区域（A 区、B 区、中路、出生点）？
2. **经济状态敏感性：** 不同经济状态（全起、半起、刚枪、Eco、手枪）下，队伍站位如何变化？
3. **跨队比较：** 如何在地图、阵营、经济标签和观察规则相同的条件下比较两支队伍，同时把对手效应保留为明确限制？
4. **样本透明度：** 如何展示比赛覆盖量，避免读者把小样本描述误认为稳定的总体规律？（系统使用 ≥5 场作为 “standard” 层级——这是工程启发式，不是统计功效分析。）

---

## 数据与分析单位

**源数据：** 来自 IEM Cologne Major 2026 的 135 个规范化 Demo bundle，覆盖 7 张竞技地图（Ancient、Anubis、Dust2、Inferno、Mirage、Nuke、Overpass）。每个 bundle 包含回合级结果、击杀事件、伤害事件、64 tick/s 选手位置、投掷物轨迹、冻结结束经济快照和压缩装备事件。

**分析单位：** **Team-map profile**——同一队伍在同一地图上的所有可用比赛。这刻意不是"战队 profile"（横跨所有地图）或"比赛 profile"（仅一场比赛）。在同一地图上比较同一队伍，可以控制地图特定的空间惯例。

**覆盖层级：**

| 层级 | 场数 | 含义 |
|------|------|------|
| Standard | ≥5 | 足以观察描述性模式 |
| Exploratory | 3–4 | 样本有限，模式为初步 |
| Insufficient | <3 | 仍可查看，但明确标注样本不足，不支持一般化结论 |

≥5 场阈值是工程启发式，不是统计显著性边界。

## 方法论

### 接触前提取

核心方法论选择是**只分析首次对手接触（伤害或击杀）之前**的时段。这避免将队伍的开局布置与对对手行动的反应混为一谈。

对每个合格回合：
1. 通过冻结结束装备、装备价值、护甲和起始余额上的确定性规则判定经济标签。
2. 选择经济适配的观察窗口：全起 20 秒、半起 12 秒、手枪/刚枪/Eco 15 秒。未知分类回退至 20 秒。
3. 提取观察截止时刻每位存活选手的位置，按区域（A、B、中路、出生点）分组。
4. 记录阵型（如 "A2·B2·中1·匪0"）。
5. 仅当观察窗口在首次对手接触前完成时，才将该样本标记为合格。

### 无机器学习

所有分类（经济状态、阵型分组、接触检测）均使用在解析游戏状态字段上运行的确定性规则。没有训练模型、没有嵌入向量、没有概率推断。这一设计选择确保完全可审计：每个分类都可追溯到特定的游戏状态特征。

### 跨队比较

两支队伍使用相同的地图、阵营、经济标签和观察规则进行比较。当前语料来自同一赛事，但两队不一定面对相同的对手；因此，这一设计统一了测量口径，却没有消除对手效应。比较限于接触前结构，明确避免：
- 回合胜负预测
- 战术意图归因
- 表现质量评分

## 系统架构 / 证据管线

```
比赛 Demo (.dem / .rar)
    │
    ▼
  规范化 Bundle（CSV：回合、击杀、位置、投掷物、
  伤害、炸弹事件、经济快照、装备事件）
    │
    ▼
  导入结果（135 已验证，0 错误）
    │
    ▼
  覆盖摘要（每 team-map 的覆盖层级）
    │
    ▼
  Team-Map Profile（manifest + 三件套）
    ├── series_metadata.json
    ├── precontact_opening_samples.csv
    └── precontact_opening_profile.csv
    │
    ▼
  研究工作台 → 跨队比较 → 证据回放
```

每个阶段产生可审计的中间产物。Profile 产物体积很小（每 profile 数十 KB），可随公开仓库分发。

## 评估与验证

系统在三个层次验证：

1. **单元和集成测试（350 passed）。** 覆盖 Demo 解析、坐标投影、回合时间线、战术发现、装备时间线、经济分类、回放状态机、跨地图 UI 契约、corpus 完整性和 Showcase 加载。

2. **发布审计（20/20 checks passed）。** 独立审计脚本 `scripts/audit_v4_release.py` 验证：
   - 135 已解析 bundle，0 导入错误
   - 117 个 corpus profile 均可被目录 API 发现
   - 所有 match entry 的 bundle 地图/队伍一致性
   - 覆盖层级与场数一致性
   - 回放契约（7 张地图可读、必需列存在、装备 HUD 可用、雷达投影正常）

3. **源 bundle 完整性。** 公开 Showcase bundle（Furia vs Falcons，Mirage，21 回合）保留完整事件表，位置数据从 1,482,670 行降采样至 185,740 行（8 Hz，约 8 倍行数缩减），GZip 使位置文件体积缩小约 45 倍。导出前后源 bundle SHA-256 不变。

## 当前结果能/不能支持什么

| 可以支持 | 不能支持 |
|---------|---------|
| 一支队伍在一张地图上的描述性接触前站位模式 | "战队默认战术"或战术意图推断 |
| 按经济状态分层的空间分布 | 胜负预测或回合结果归因 |
| 相同地图与测量口径下的跨队描述 | 将差异因果归结为队伍偏好，而忽略对手与比赛上下文 |
| 从 Demo 到发现的可复现可审计证据链 | 统计显著性结论 |
| 覆盖层级对应的样本透明度 | 超出可用场数的泛化 |

## 有效性威胁与局限

1. **生态效度。** 接触前结构是完整回合的一个薄切片。12–20 秒观察窗口捕获初始布置，但不包括回合中期适应、道具使用或残局情况。
2. **对手混杂。** 观察到的站位不仅与目标队伍有关，也会受到对手、已获得的信息、道具、声音、前序回合调整和比赛上下文影响。统一测量口径能让输出具备可比性，但当前数据并不是匹配对手样本，不能消除这一混杂。
3. **赛事特定上下文。** 所有数据来自单一赛事（IEM Cologne Major 2026）。结果可能无法泛化至其他赛事、阵容版本或游戏补丁。
4. **地图覆盖。** 中文区域词典和详细战术分析仅完成 Mirage。非 Mirage 地图回退至区域级（A/B/中路/Other）分组，无子区域标签。
5. **样本量。** “Standard”层级（≥5 场）是工程便利，不是统计验证的阈值。按阵营和经济状态分层、再排除过早交火回合后，即使五场比赛也可能只剩很少的可用样本。
6. **解析器依赖。** 管线依赖 Awpy 进行 Demo 解析。解析器更新或 CS2 Demo 格式变化可能需要重新验证。

## 可复现性与公开 Showcase

代码与轻量 Showcase 已为 GitHub 公开发布做好准备。但完整的 67 GB 原始 Demo 和处理后 bundle **不随仓库分发**（体积与再分发边界）。源代码采用 MIT License；游戏衍生素材不属于该许可证，边界详见 `THIRD_PARTY_NOTICES.md`。

**公开 Showcase bundle**（`data/showcase/furia-falcons-mirage/`，2.78 MB）允许任何用户在不下载语料库的情况下体验完整回放管线：

```bash
pip install -r requirements.txt
streamlit run app.py  # 点击"回放"→"加载公开 Showcase"
```

Showcase 包含真实比赛（Furia vs Falcons，Mirage，21 回合）的全部事件表，位置数据降采样至 8 Hz。它演示雷达回放、道具动画和 OB 式装备 HUD。它**不进入**跨队比较结论。

希望构建自己语料库的用户可使用提供的导入脚本配合合法获取的 CS2 Demo 文件。

## 结论

CS Tactical Lens 展示了一个能够运行的研究原型，用于对职业 CS2 比赛的接触前结构进行可审计分析。它把输出约束在描述性证据范围内并明确标注覆盖限制，为基于证据的战术讨论提供了具体起点，但不声称能够恢复队伍意图。分析运行时由可检查的 Python 组件构成；采用 MIT License 的代码可供公开检查和扩展，游戏素材边界另行说明。

## 答辩用 8 个问题

### 1. 为什么只研究首次实际交火前？

首次伤害或击杀前能够减少“发生直接交火后被迫调整”这一类干扰，但绝不是不受对手影响的纯净窗口。选手仍可能根据声音、道具、已知对手倾向和前序回合进行反应；因此它只是较窄、较容易复核的描述窗口，不能直接代表开局意图。

### 2. 为什么不同经济局使用不同观察秒数？

不同经济状态往往伴随不同的装备约束与回合节奏，但经济状态本身并不直接决定选手移动速度，也不能推出某种战术意图。12/15/20 秒是为了在不同局型下取得可用样本与可比性的工程规则；任何在观察时刻前已经发生首次实际交火的回合仍会被排除。这些秒数不是模型学习结果，也不是已证明的最优参数。

### 3. 为什么重复站位不能直接叫默认战术？

重复站位只说明"在样本范围内，队伍多次以相同人数分布开始回合"，但不说明这是教练设计的默认战术，还是选手自发形成的习惯，还是对手特定策略的产物。将此称为"默认战术"超出了证据可以支持的范围。

### 4. 样本不足时系统如何提示？

分为三层：standard（≥5 场）、exploratory（3–4 场）和 insufficient（<3 场）。当前工作台允许查看已有 profile，并在选择器和页面中显示覆盖标签；样本不足时应直接提示，而不是隐藏数据或制造稳定结论。

### 5. 8 Hz Showcase 与本地完整数据有什么区别？

完整本地数据保留 64 tick/s（约每秒 64 个位置样本），Showcase 降采样至 8 Hz（每秒约 8 个样本），以 GZip 压缩存储。事件表（击杀、道具、经济、装备）完整保留。Showcase 用于演示回放交互，不进入跨队比较；它对 GitHub 克隆用户立即可用。

### 6. 项目最主要的有效性威胁是什么？

生态效度——接触前结构只占完整回合的一小部分。12–20 秒观察窗口能捕捉开局布置，但对中期适应、道具使用和残局表现没有解释力。此外，所有数据来自单一赛事，泛化到其他赛事或阵容版本需要额外验证。

### 7. 为什么不用机器学习模型？

可审计性要求：确定性规则的每个输出都可追溯到具体的游戏状态字段，而 ML 模型（即使是简单的）也会引入无法直接从单行数据解释的权重和偏置。在没有训练数据集的约束下，确定性规则更透明、更易调试、更适合这个阶段的探索性分析。

### 8. AI 在项目中承担了什么、作者本人承担了什么？

AI 完成了大部分代码实现、测试编写和文档初稿。作者负责产品方向、CS 领域判断、定义分析边界、否定无效指标、准备和检查数据、以及最终验收。这是 AI 辅助工程与人工迭代验证的协作模式。
